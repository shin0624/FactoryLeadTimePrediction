# 합성 데이터 파이프라인 검증 — 결과 분석

> 목적 : A_RealDataLeadTime의 실패(R² −0.35) 원인을 확정하기 위해, **정답을 알고 있는 데이터**로 파이프라인을 검증
> 생성 규칙 : `LeadTime = 8.0 + 0.8×납기여유 + 1.5×거래처재고 − 1.2×운송빈도 + N(0, σ)`
> 조건 : 176행 / σ=3 / seed=42 (실데이터와 행 수·하이퍼파라미터 동일)

---

## 1. 결론 — 파이프라인은 정상이다

**가설 3(코드 버그)은 배제되었고, 가설 2(176행 부족)는 반증되었다.**

| | 합성 데이터 | 실데이터 | 차이 |
|---|---|---|---|
| 행 수 | 176 | 176 | **동일** |
| 하이퍼파라미터 | 동일 | 동일 | **동일** |
| 코드 | 동일 파이프라인 | 동일 파이프라인 | **동일** |
| **교차검증 평균 R²** | **+0.7862** | **−0.3464** | **1.13** |
| **RMSE 표준편차** | **0.24** | **1.24** | **5.2배** |

같은 코드·같은 행 수·같은 설정에서 **R²가 +0.79 vs −0.35**로 갈렸다.
→ 차이를 만든 것은 **데이터에 신호가 있는지 여부**뿐이다.

### 실데이터 실패 원인 확정

```
가설 1 : 데이터에 리드타임을 결정하는 정보가 없다   → ✅ 확정 (유일한 원인)
가설 2 : 176행은 너무 적다                        → ❌ 반증 (176행으로도 R² 0.79 달성)
가설 3 : 파이프라인 코드에 버그가 있다              → ❌ 배제 (정상 작동 확인)
```

> **실무적 함의 :** 해결책은 **데이터를 더 모으는 것이 아니다.**
> 거래처 납기·거래처 재고·운송 스케줄 같은 **새로운 컬럼을 수집**해야 한다.
> 행 수를 1,000행으로 늘려도 지금 컬럼 구성으로는 여전히 실패한다. 투자 방향이 달라지는 판단이다.

→ **판정 기준을 교차검증 평균 R² ≥ 0.70 으로 수정한다.** 단일 분할(35행)은 변동이 커서 판정 기준으로 부적합하다.

## 3. 실험 A : 행 수 효과 (σ=3)

| 행 수 | 학습 R² | 검증 R² | 격차 | 사전 예측(검증) |
|---|---|---|---|---|
| **176** | 0.971 | **0.748** | 0.223 | 0.822 |
| 500 | 0.978 | **0.851** | 0.128 | 0.844 |
| 1,000 | 0.964 | **0.879** | 0.084 | 0.851 |
| 3,000 | 0.922 | **0.877** | 0.045 | 0.858 |

**기대 패턴이 정확히 재현되었다 :**
- 학습 R² 0.971 → 0.922 (하락)
- 검증 R² 0.748 → 0.877 (상승)
- 격차 0.223 → 0.045 (**5배 축소**)

### 읽는 법

격차가 좁혀지는 것이 **"외우기 → 학습하기"로의 전환**이다.

- 176행 : 모델이 141개 행의 개별 특성을 외운다 (학습 0.971인데 검증 0.748)
- 3,000행 : 외울 수 없을 만큼 많으니 일반 규칙을 찾는다 (격차 0.045)

1,000행에서 검증 R² 0.879가 **이론 상한 0.877을 사실상 달성**했다. 3,000행에서도 0.877로 더 오르지 않는다.
→ **노이즈 한계에 도달한 것이다.** 데이터를 더 모아도 이 이상은 불가능하다. 이것이 "충분한 데이터"의 정의다.

## 4. 실험 B : 노이즈 효과 (176행)

| σ | 검증 R² | 이론 상한 | 상한 대비 달성률 |
|---|---|---|---|
| 1 | **0.961** | 0.981 | 98% |
| 3 | **0.748** | 0.877 | 85% |
| 5 | **0.441** | 0.732 | 60% |
| 8 | **−0.030** | 0.533 | — |

**노이즈가 커질수록 상한에서 멀어진다.** σ=1에서는 상한의 98%를 달성하는데, σ=8에서는 R²가 음수가 된다.

### σ=8에서 R² −0.030 — 실데이터와 같은 상태

σ=8일 때 **이론적으로는 R² 0.533이 가능한데 실측은 −0.030**이다. 신호가 분명히 존재하는데도(계수 +0.8/+1.5/−1.2) 176행으로는 노이즈에 묻혀 찾아내지 못한다.

→ 실데이터의 R² −0.35가 이 상태와 유사하다. 다만 실데이터는 **노이즈가 커서**가 아니라 **신호 자체가 없어서**다.

> **배운 것 :** R² 1.0은 목표가 될 수 없다. 현실 데이터에는 항상 설명 불가능한 변동이 있고, 그만큼은 어떤 모델도 맞힐 수 없다.
> **이론 상한을 넘으면 오히려 데이터 누출을 의심해야 한다.**

## 5. 기여도 검증 — 가장 중요한 수확

### 5-1. 영향력 순위 검증 ✅ 통과

| 피처 | 실측 평균 기여 크기 | 정답 기여 std | 비율 |
|---|---|---|---|
| 납기여유일 | **9.48** | 6.70 | 1.41 |
| 거래처재고 | **7.33** | 4.33 | 1.69 |
| 운송빈도 | **3.43** | 2.08 | 1.65 |
| 생산량(Kg) | 1.67 | **0 (무관)** | — |
| 공정시간(분) | 1.51 | **0 (무관)** | — |
| 요일 | 0.43 | **0 (무관)** | — |

**순서가 정답과 완벽히 일치한다** : 납기여유일 > 거래처재고 > 운송빈도

> 실측값이 정답의 1.4~1.7배로 일정하게 부풀어 있다. 이는 트리 모델이 기여도를 분배하는 방식 때문이며, **절대값보다 상대 순위가 의미 있다**는 뜻이다.

**노이즈 3개도 통과했다.** 최대 1.67 < 운송빈도 3.43. 완전히 0은 아니지만(176행에서 트리가 우연한 패턴을 잡음) 진짜 피처보다 명확히 작다.

→ **기여도 도구가 정상 작동한다.** 실데이터에서는 이것을 검증할 방법이 없었다.

### 5-2. ⚠️ 개별 기여도 부호 — 내 검증 설계가 틀렸다

출력을 보면 부호가 정답 계수와 어긋난다 :

```
샘플1: 납기여유 +8.85 (정답 +0.8)  거래처재고 -5.47 (정답 +1.5)  운송빈도 +6.88 (정답 -1.2)
샘플2: 납기여유 -5.91 (정답 +0.8)  거래처재고 -4.93 (정답 +1.5)  운송빈도 +1.23 (정답 -1.2)
```

**이것은 버그가 아니고, 내가 출력에 `정답 : +0.8` 식으로 나란히 찍게 만든 것이 잘못된 비교였다.**

기여도 부호는 이렇게 결정된다 :

```
기여도 부호 = (계수 부호) × (그 샘플의 피처값이 평균보다 큰가 / 작은가)
```

샘플1을 검산해보면 전부 **정합적**이다 :

| 피처 | 기여도 | 해석 | 정답 계수 | 모순? |
|---|---|---|---|---|
| 납기여유일 | **+8.85** | 평균(15.5)보다 **긴** 납기 → 리드타임 증가 | +0.8 | ✅ 없음 |
| 거래처재고 | **−5.47** | 평균(5.0)보다 **낮은** 재고 → 리드타임 감소 | +1.5 | ✅ 없음 |
| 운송빈도 | **+6.88** | 평균(4.0)보다 **낮은** 빈도 → 리드타임 증가 | −1.2 | ✅ 없음 |

→ **개별 샘플의 기여도 부호를 계수 부호와 직접 비교하는 것은 애초에 불가능하다.**
계수의 부호를 확인하려면 **피처값이 증가할 때 기여도가 어떻게 변하는지(기울기)** 를 봐야 한다.

**이것이 이번 실습에서 정정된 가장 중요한 오개념이다.** 체크리스트 6번(기여도 부호 검증)은 설계가 잘못되었으므로 폐기한다.

### 5-3. ✅ 기준값(bias) 문제 해결 — A의 미해결 질문에 답

실데이터에서 기준값이 42.5 / 54.2 / 39.2로 흔들린 것이 과적합 탓인지 ML.NET의 정상 동작인지 미해결로 남겼다. **합성 데이터에서도 14.13 / 22.81 / 32.01로 흔들렸다(편차 17.88일).**

검산해보면 항등식 자체는 **정확히 성립한다** :

| 샘플 | Score | 기여도 합 | 계산된 bias | bias + 합 |
|---|---|---|---|---|
| 1 | 26.43 | +12.29 | 14.13 | **26.42** ✅ |
| 2 | 15.76 | −7.05 | 22.81 | **15.76** ✅ |
| 3 | 19.14 | −12.85 | 32.01 | **19.16** ✅ |

→ 내가 `bias = Score − 기여도합`으로 **역산**했으니 항등식은 당연히 성립한다. 순환 계산이었다.

**결론 : 이 "기준값"은 모델의 bias가 아니다.** `normalize: false`일 때 ML.NET의 기여도는 각 트리의 분할 경로를 따라 분배된 값이며, SHAP처럼 `모델 bias + Σ기여도 = Score` 항등식을 보장하지 않는다. LightGBM은 트리 200개의 합이므로 샘플마다 통과 경로가 달라 분배 결과도 달라진다.

→ **"기준값에서 출발한다"는 해석은 쓸 수 없다. 출력에서 제거하는 것이 맞다.**
→ 실데이터에서 본 현상은 **과적합 탓이 아니라 ML.NET 기여도의 정상 동작**이었다. (A 결과분석 5-1절 수정 필요)

## 7. A_RealDataLeadTime 결과분석 문서 수정 사항

이번 실험 결과로 A 문서의 두 곳이 정정되어야 한다.

### 7-1. 원인 ③ "데이터가 176행뿐이다" → 반증됨

> 기존 : "176행 × 피처 6개는 트리 모델이 일반화할 만한 양이 아니다"
> **정정 : 176행으로도 신호가 있으면 R² 0.79가 나온다. 행 수가 아니라 신호 부재가 원인이다.**

### 7-2. 5절 "기여도 이상 신호" → ML.NET 정상 동작

> 기존 : "과적합된 모델의 기여도는 해석하면 안 된다"
> **정정 : 기준값이 샘플마다 다른 것은 과적합과 무관한 ML.NET 기여도의 정상 동작이다.**
> 단, "기여도 합이 비정상적으로 큰 음수"는 여전히 과적합 신호로 유효하다(합성데이터는 −12.85~+12.29로 균형).

## 8. 이번 실습에서 배운 것

### 8-1. 방법론

| 개념 | 체감한 방식 |
|---|---|
| **합성 데이터로 도구 검증** | 정답을 알고 있으니 기여도 순위가 맞는지 대조 가능 |
| **이론 상한의 존재** | 노이즈만큼은 어떤 모델도 설명 못 함. R² 1.0은 목표가 아니다 |
| **상한 초과 = 누출 신호** | 실험 B에서 전부 "정상"이 나온 것이 누출 없음의 증거 |
| **데이터 양 vs 정보량** | 1,000행에서 상한 도달. 그 이상은 무의미. "충분한 데이터"의 정의 |
| **단일 분할의 불안정성** | 35행 검증은 0.748, 교차검증은 0.786. 소규모에서는 교차검증이 필수 |

### 8-2. 정정된 오개념 (가장 가치 있는 부분)

1. **개별 기여도 부호 ≠ 계수 부호** — 기여도는 "평균 대비 방향"이므로 샘플마다 부호가 바뀐다
2. **`Score − 기여도합`은 모델 bias가 아니다** — 역산이므로 항등식이 자동 성립하는 순환 계산
3. **ML.NET 기여도는 SHAP이 아니다** — `normalize: false`에서도 가법성(additivity)을 보장하지 않는다

## 10. 다음 단계 — 유전 알고리즘(GA)

파이프라인 검증이 끝났으므로 원래 계획대로 GA로 넘어간다.

```
[A] 실데이터 리드타임 예측  → R² -0.35 (정보 부재로 실패, 원인 확정)
[B] 합성데이터 파이프라인 검증 → R² +0.79 (파이프라인 정상 입증)  ← 완료
[C] 유전 알고리즘(GA) 구현   ← 다음
```

**왜 GA인가 :** 이 데이터셋의 공식 알고리즘이다(가이드북 p.17).

> "생산된 물건 단위는 정수 조건이 필요하므로 조합 최적화 문제는 **정수계획법**이며 다항 시간 내에 풀 수 없는 **NP-hard** 문제이다."

즉 이 데이터는 **예측(prediction) 문제가 아니라 최적화(optimization) 문제**다.
- 생산량은 "예측할 대상"이 아니라 **"우리가 결정할 의사결정 변수"**
- 목표 : 출고일에 맞춰 날짜별 생산량을 배분해 **재고를 최소화**
- 적합도 함수는 가이드북 p.30-31에 그대로 제시되어 있음
- 유전자 497개 (전체 날짜 범위), 외부 라이브러리 없이 C# 구현 가능

A에서 "생산량 예측은 이 데이터에서 안 된다"고 결론 낸 것과 B에서 "파이프라인은 정상"임을 확인한 것이 합쳐져, **ML이 아니라 최적화로 가야 하는 이유**가 수치로 뒷받침되었다.
