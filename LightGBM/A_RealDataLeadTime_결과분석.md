# 실데이터 리드타임 예측 — 2단계 결과 분석

> 데이터셋 : KAMP 「표면처리 공급망최적화 AI 데이터셋」 (M21 전기아연도금, 177행)
> 모델 : LightGBM 회귀 (ML.NET 5.0)
> 예측 대상 : 리드타임(일) = 1차 출고날짜 − 생산일자

---

## 1. 한 줄 요약

**모델은 실패했습니다. 그리고 그 실패는 정확히 예상된 것이며, 이번 실습의 결과물입니다.**

생산 데이터만으로는 리드타임을 예측할 수 없다는 것이 수치로 증명되었습니다. 중요한 건 "모델이 안 된다"는 사실 자체가 아니라, **그것을 판별하는 절차를 갖췄다**는 점입니다.

## 3. 이 숫자들이 뜻하는 것

### 3-1. R² 음수 = 평균 찍기보다 못하다

R²는 "평균값으로 예측하는 것 대비 얼마나 나은가"를 재는 지표입니다.

```
R² =  1.0  → 완벽한 예측
R² =  0.0  → "항상 19.4일"이라고 답하는 것과 동일
R² <  0.0  → 평균 찍기보다 못함  ← 지금 상태 (−0.35)
```

교차검증 평균 R²가 **−0.3464**입니다. 즉 **모델을 쓰는 것보다 "무조건 19.4일"이라고 답하는 게 낫습니다.** 모델이 피처를 보고 판단할 때마다 오히려 정답에서 멀어집니다.

### 3-2. 과적합이 명확하게 잡혔다

```
학습 데이터  R² = +0.58,  RMSE =  6.50일   ← 잘 맞힌다
검증 데이터  R² = −0.27,  RMSE =  9.37일   ← 못 맞힌다
             ↑ 격차 0.85
```

학습 데이터에서는 R² 0.58로 그럴듯합니다. 하지만 처음 보는 데이터에서는 음수로 떨어집니다. **이것이 과적합의 교과서적 패턴입니다** — 모델이 패턴을 학습한 게 아니라 149개 행을 외운 것입니다.

> **만약 1단계에서 `TrainTestSplit`을 하지 않았다면** R² 0.58만 보고 "꽤 괜찮은 모델"이라고 결론 내렸을 것입니다. 검증 데이터를 분리하는 것이 왜 필수인지 보여주는 결과입니다.

### 3-3. 교차검증이 단일 분할보다 가혹하다

| 방식 | RMSE |
|---|---|
| 단일 분할 (27행 검증) | 9.37일 |
| 5-Fold 교차검증 평균 | **10.84일** |

단일 분할 결과(9.37일)는 **운이 좋았던 것**입니다. 교차검증을 돌리니 RMSE가 9.37~12.47일로 흔들리고, 평균은 10.84일로 **베이스라인 9.9일을 완전히 넘어섭니다.**

Fold별 RMSE 폭이 **9.37 ~ 12.47일 (표준편차 1.24)** 로 넓고, Fold 5의 R²는 **−0.92** 까지 떨어집니다. 어느 35행이 검증에 뽑혔는지에 따라 결과가 크게 달라진다는 뜻 — **176행으로는 안정적인 패턴이 잡히지 않습니다.**

## 4. 왜 실패했는가 — 근본 원인

### 원인 ① 피처가 라벨과 거의 무관하다

1단계에서 실측한 상관계수:

| 피처 | 리드타임 상관계수 |
|---|---|
| 공정 소요시간 | +0.171 |
| 월 | −0.096 |
| 생산량(Kg) | +0.085 |
| 요일 | +0.077 |
| 시작 시각 | −0.000 |

**전부 0.2 미만입니다.** 상관이 거의 없는 피처로는 예측이 불가능합니다. 모델의 문제가 아니라 **입력 정보 자체가 부족**한 것입니다.

### 원인 ② 리드타임을 결정하는 진짜 변수가 데이터에 없다

리드타임 = "생산 후 거래처에 나가기까지의 일수" 입니다. 이것을 결정하는 건:

- 거래처의 **발주 납기** ← 데이터에 없음
- 거래처의 **재고 상황** ← 데이터에 없음
- **운송 스케줄** ← 데이터에 없음

반면 우리가 가진 건 생산량, 공정시간, 요일 등 **공장 내부 정보뿐**입니다. 공장이 아무리 빨리 만들어도 거래처가 2주 뒤에 달라고 하면 리드타임은 14일입니다. **공장 데이터로 거래처 사정을 맞히려 한 셈입니다.**

### 원인 ③ 데이터가 176행뿐이다

LightGBM 같은 부스팅 모델은 보통 수천~수만 행을 전제합니다. 176행 × 피처 6개는 트리 모델이 일반화할 만한 양이 아닙니다. 교차검증 표준편차 1.24가 그 불안정성을 보여줍니다.

## 5. 기여도 분석에서 발견된 이상 신호 ⚠️

기여도 출력에서 **정상이 아닌 패턴**이 두 가지 나왔습니다. 이것이 과적합의 추가 증거입니다.

### 5-1. 기준값(bias)이 샘플마다 다르다

| 샘플 | 예측값 | 기여도 합 | 계산된 기준값 |
|---|---|---|---|
| 1 | 12.23일 | −30.28 | **42.51일** |
| 2 | 13.66일 | −40.53 | **54.19일** |
| 3 | 16.85일 | −22.38 | **39.23일** |

**기준값은 모델 전체에 하나뿐인 상수여야 합니다.** 그런데 42.5 / 54.2 / 39.2로 다릅니다.

> 이유: `normalize: false`일 때 ML.NET의 기여도는 **각 트리의 분할 경로를 따라 분배된 값**이며, 엄격한 `bias + Σ기여도 = Score` 항등식(SHAP의 성질)을 보장하지 않습니다. LightGBM은 트리 200개의 합이므로 샘플마다 통과하는 경로가 달라 분배 결과도 달라집니다.
>
> 따라서 **"기준값에서 출발한다"는 해석은 쓸 수 없습니다.** 기여도는 **부호와 상대적 크기**로만 읽어야 합니다.

### 5-2. 모든 피처가 음수 기여를 한다

샘플 1과 2에서 **6개 피처 전부가 마이너스**입니다. 기여도 합이 −30, −40일인데 예측값은 12~13일입니다.

이건 "모든 요인이 리드타임을 줄였다"는 뜻이 아니라, **모델 내부가 비정상적으로 큰 양수 기준점에서 큰 음수들을 빼는 구조로 학습되었다**는 신호입니다. 리드타임 범위가 2~55일인데 한 피처가 −10.9일을 기여하는 것도 과도합니다.

→ **과적합된 모델의 기여도는 해석하면 안 됩니다.** 모델 자체가 신뢰할 수 없으므로 그 근거도 신뢰할 수 없습니다.

### 5-3. 00_LeadTimeTest(더미데이터)와의 비교

| | 더미데이터 | 실데이터 |
|---|---|---|
| 기여도 0.00 피처 | 온도, 작업자수 | 없음 |
| 원인 | **다중공선성** (피처 3개가 완벽 상관) | — |
| 패턴 | 투입량 하나만 사용 | 6개 전부 사용 (과도하게) |

더미데이터에서는 "트리가 피처를 안 썼다"는 문제였고, 실데이터에서는 "트리가 모든 피처를 과도하게 썼다"는 반대 문제입니다. **같은 기여도 도구로 두 가지 다른 병증을 진단한 셈입니다.**

## 6. 하이퍼파라미터는 범인이 아니다

`MinimumExampleCountPerLeaf = 15`, `NumberOfLeaves = 16`, `L2Regularization = 1.0` — 이미 과적합 방지를 걸어둔 설정입니다. 그런데도 과적합이 났습니다.

> **결론: 튜닝으로 해결되지 않습니다.** 파라미터를 더 조여도 R²는 0에 가까워질 뿐(= 평균 찍기에 수렴) 양수가 되지 않습니다. 원인이 모델 설정이 아니라 **입력 정보의 부재**이기 때문입니다.

확인해보고 싶다면 `MinimumExampleCountPerLeaf`를 2 / 5 / 15 / 30 / 50으로 바꿔가며 돌려보세요. 예상되는 패턴:

```
값 작음(2)   → 학습 R² 높음 / 검증 R² 더 낮음   (과적합 심화)
값 큼(50)    → 학습 R² 낮음 / 검증 R² ≈ 0       (평균 찍기에 수렴)
```

**어느 쪽도 쓸 만한 모델이 아닙니다.** 이것을 직접 확인하는 것이 좋은 실험입니다.

## 7. 이번 실습에서 실제로 얻은 것

모델은 실패했지만, 아래는 전부 성공했습니다.

### 7-1. 기술적 습득

- CSV 실데이터 파싱 — 인코딩(CP949→UTF-8), 따옴표 안 콤마(`"13,550"`), 혼재된 시간 포맷(`7:10`/`10:40`), 빈 문자열 결측
- Raw DTO / Feature DTO 분리 설계
- 2-pass 피처 엔지니어링 (`GroupBy` 집계 → 변환)
- `LoadFromEnumerable` → `IDataView` → `Concatenate` → LightGBM
- `TrainTestSplit`, `Evaluate`, `CrossValidate`
- `CalculateFeatureContribution` 실데이터 적용

### 7-2. 개념적 습득 (더 중요)

| 개념 | 이번에 체감한 방식 |
|---|---|
| **베이스라인 설정** | 9.9일을 먼저 계산해둔 덕에 "RMSE 9.37"이 좋은 게 아님을 즉시 알았다 |
| **과적합 판별** | 학습 R² 0.58 vs 검증 R² −0.27 의 격차로 수치 확인 |
| **교차검증의 필요성** | 단일 분할 9.37일 → 교차검증 10.84일. 단일 분할이 운이었음이 드러남 |
| **데이터 누출 차단** | 출고횟수(상관 +0.295, 가장 높음)를 설계로 배제. 성능 좋은 피처 ≠ 쓸 수 있는 피처 |
| **기여도 해석의 한계** | 과적합 모델의 기여도는 해석 불가. bias 항등식이 성립하지 않음을 직접 확인 |

> **가장 큰 수확:** 데이터 누출 피처를 넣었다면 성능이 올라가 "성공한 모델"로 보였을 것입니다. 그걸 의도적으로 배제했기 때문에 **정직한 실패**를 얻었습니다. 실무에서 이 구분을 못 하면 배포 후에 망합니다.

## 8. 그래서 다음에 무엇을 할까

### 선택 A. 타깃을 바꾼다 (추천)

리드타임은 포기하고, **데이터에 실제로 변동이 있는 타깃**으로 옮깁니다.

| 후보 | 비고 |
|---|---|
| **일별 출고량(수요) 예측** | 가이드북 GA가 "이미 안다고 가정"한 값. 이걸 ML로 예측하면 GA와 결합 가능 |
| 출고 분할 횟수 예측 | 다중분류 연습. 분포 1~10회(평균 3.7) |
| 완전출고 소요일수 | 재고 최소화 목적에 직결 |

### 선택 B. 가이드북의 정답 경로로 간다

이 데이터셋의 공식 알고리즘은 **유전 알고리즘(GA)** 입니다. 예측이 아니라 **최적화** 문제이기 때문입니다.

```
[가이드북]  출고량 = 기지(旣知)  → GA로 날짜별 생산량 스케줄 최적화
[확장]      출고량 = LightGBM 예측 → 그 예측값으로 GA 실행
```

GA는 외부 라이브러리 없이 C#으로 150줄 정도면 구현됩니다(적합도 함수가 가이드북 p.30-31에 그대로 있음). "ML ≠ AI의 전부"를 배우는 좋은 연습입니다.

### 선택 C. 현재 모델을 파라미터 실험용으로 더 써본다

6절의 `MinimumExampleCountPerLeaf` 실험을 돌려 **과적합↔평균수렴 스펙트럼**을 눈으로 확인합니다. 모델은 못 쓰지만 교육적 가치는 있습니다.
